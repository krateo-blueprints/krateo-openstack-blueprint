# Image supply chain

Issue #316. Two parts: what is in place, and a pinning decision that is still open.

## In place

| What | Where | When it runs |
| --- | --- | --- |
| **Inventory.** Every image a published chart can run, from renders at defaults and with every off-by-default manifest on, plus every `images.tags` entry. Each image's registry, tag, publisher, and whether the registry serves it anonymously. | `hack/images.yaml` (machine-readable), [images.md](images.md) (table), both generated by `hack/gen-image-inventory.py` | Offline on every pull request (`lint.yaml`): fails if a chart's images differ from the inventory, or if an image is recorded as not pullable |
| **Publishers.** Every image's registry namespace has a named publisher and build source, and every entry matches an image. | `hack/image-sources.yaml` | Same gate |
| **Registry re-measurement.** Each image is still served anonymously, in a format containerd pulls (not Docker Registry v1, #115), with a linux/amd64 manifest and a downloadable config blob. | `hack/gen-image-inventory.py --resolve` | `image-scan.yaml`: weekly, on each release tag, and on a push that changes the inventory |
| **CVE scan.** Trivy (pinned version, tarball checked against a digest written in the workflow) scans every pullable image as linux/amd64. A CRITICAL finding fails unless `hack/image-cve-allowlist.yaml` has an entry for that CVE, image and package that has not expired. | `.github/workflows/image-scan.yaml`, `hack/check-image-cves.py` | Same as above. The judging rules also run offline on every pull request (`--self-test`) |

**Why the scan is not on every pull request.** Not for speed. The first full run (image-scan run 44188443677) scanned
all 58 images in 2.6 minutes of wall time, 18 runner-minutes in total, 11 to 49 seconds per image. The reason is that
a pull request which changes no image can't change the result. Only a newly published CVE can, and gating every
pull request on that would turn unrelated changes red on upstream news. So the scan runs:
- on a push that changes `hack/images.yaml`, which a pull request that changes an image must regenerate to pass
  `lint.yaml`;
- weekly, which catches newly published CVEs;
- on each release tag.

**Exceptions.** An allowlist entry names the CVE, the image exactly as the inventory writes it, and the package. It
carries a reason and an expiry at most 120 days ahead. An expired entry stops covering its finding. An entry that
covers no finding is reported, not failed: images on series tags are rebuilt upstream almost daily, so a finding can
disappear between two runs with nothing changed here. The expiry bounds how long a leftover entry can stay.

### First scan, 2026-11-17

Trivy 0.76.1, linux/amd64, run 44188443677.

- **177 CRITICAL findings (167 distinct CVE, image and package keys) in 43 of the 58 images**, and 3,237 HIGH.
- **Most widespread:** PyJWT 2.11.0 (CVE-2026-102268, fixed in 2.14.0) in 29 airshipit OpenStack service images,
  and Go stdlib 1.24.4 (CVE-2025-68121) in 14 findings.
- **Most per image:**
  - `docker.io/nginx:1.13.3`: 54. Debian 9, past end of support. ironic runs it at defaults.
  - `quay.io/airshipit/docker:27.5.0`: 19. image_repo_sync only; no default render runs it.
  - `docker.io/xrally/xrally-openstack:2.0.0`: 11. Ubuntu 18.04, helm test pods only.
  - `docker.io/powerdns/pdns-auth-49:4.9.18`: 8.
  - `quay.io/airshipit/memcached:1.6.32`: 7.
  - Each of the four Kolla gnocchi images: 6.
- **Past end of support** (Trivy's OS metadata): `nginx:1.13.3` (Debian 9), `xrally-openstack:2.0.0` (Ubuntu 18.04),
  `airshipit/rabbitmq:3.10.18` and `-management` and `kubernetes-entrypoint:…-ubuntu_focal` (Ubuntu 20.04),
  `docker:17.07.0` (Alpine 3.6) and `airshipit/docker:27.5.0` (Alpine 3.21).

Every finding is in `hack/image-cve-allowlist.yaml` with its measured facts and a shared expiry, 2027-02-15. That
date is when the remediation is due. The entries don't claim the findings are harmless; they only make the gate fail
on anything new.

## Open: how to pin images

The inventory and the scan describe the images as they are today. Today most of them are not pinned, and the scan
inherits that weakness: it scans what a tag points to on the day it runs, not what a cluster pulled earlier.

### Measured, 2026-11-17

All from quay's tag-history API (`/api/v1/repository/<repo>/tag/?specificTag=<tag>`) and anonymous manifest requests.

- **35 of the 58 images use a release-series tag** (31 `quay.io/airshipit/*:2026.1-ubuntu_noble` and 4
  `quay.io/openstack.kolla/gnocchi-*:2026.1-ubuntu-noble`). Over the last 30 days, each airshipit series tag was
  pushed **27 to 32 times, every push a new digest** (keystone: 27). The same chart version installs a different
  build each day. With `pullPolicy: IfNotPresent`, two nodes that first pulled on different days run different
  builds of the same service.
- **Airship also publishes dated tags**, `2026.1-ubuntu_noble-YYYYMMDD`, one per build. Five sampled keystone dates
  back to 2026-04-15 were each pushed once and carry no expiry. They are **not guaranteed immutable**, though:
  `ceph-config-helper:ubuntu_jammy_20.2.4-1-20260828` was pushed twice, with two digests, on the same day.
- **A digest that only a series tag held can disappear.** Of two older keystone series-tag digests sampled, the one
  from 2026-08-05 still resolves and the one from 2026-09-29 returns 404. A `@sha256:` pin is only as durable as
  the tag that keeps its manifest alive.
- **Kolla publishes no dated or commit tags for gnocchi.** It publishes only series tags, and quay keeps no history
  for them (one entry, pushed 2026-11-17).
- **Already immutable in form:** 3 commit-SHA tags (kubernetes-entrypoint ×2, porthole) and 6 dated tags. One image
  is digest-pinned: `docker.io/bitnami/kubectl@sha256:…` in libvirt, which never runs on kind. Docker Hub has no tag
  history API, so whether its version tags (`rabbitmq:3.13-management`, `redis:7.2.17`, …) have been rebuilt can't
  be measured there. They are treated as rebuildable.

### The constraint

On kind, images are side-loaded (`tools/kind-load-images.sh`: `docker pull --platform linux/amd64`, `kind load`).
`docker save` writes the single-platform image and drops the registry's index digest, so containerd can't match a
`@sha256:` reference and the pod tries to pull (#72). The loader refuses digest references for that reason. Any
image the kind path loads must be referenced by tag.

### Options

**A. Immutable tag in the chart, digest recorded in the inventory and verified in CI.** Charts reference a dated,
commit or version tag (for airshipit, `2026.1-ubuntu_noble-YYYYMMDD`). `hack/images.yaml` already records each
tag's digest. Two gates turn that record into the pin:
1. Offline, per pull request: fail on any tag that isn't in an immutable form. This is the "CI fails on an unpinned
   image" acceptance criterion.
2. Weekly and per release: fail when a tag's digest differs from the record. Today `--resolve` only reports this.

Works unchanged on kind. A re-push like `ceph-config-helper`'s is caught by gate 2, not prevented. A dated tag is
also the reference that keeps its manifest alive, so it doesn't share the digest-disappears risk. Bumps become
explicit: a weekly job proposes the newest dated tag, the scan runs on that pull request, and the release states
what it installs. **Not available for the 4 Kolla gnocchi images**, which have no immutable tag.

**B. Digests in the charts, with a kind-specific loader.** Every chart reference becomes `@sha256:`. The kind path
would need a loader that keeps the index, e.g. an OCI layout imported with its index into containerd instead of
`docker save`. That loader is unmeasured: whether an arm64 node imports an amd64-only child under the index digest
is exactly the kind of property #72 found false. Digests are unreadable in values and reviews, and the 404 above
shows a digest outlives its upstream only while a tag holds it, so B still needs A's tags or C's mirror underneath.

**C. Mirror into a registry this org controls.** Copy each image into `ghcr.io/krateo-blueprints/…` under an
immutable tag. Copying by manifest keeps the index digest. Charts reference the mirror by tag, with the digest
recorded as in A. This removes dependence on upstream retention and rebuilds (#115 was an upstream image no one
could pull), and gives one place to sign, attest and attach SBOMs. Cost: a mirror workflow and its storage, and
security fixes arrive only when this repo bumps.

### Recommendation

**A now, C for the images A cannot pin.** Repoint the 31 airshipit series-tag images at their dated tags and turn
on both gates. Mirror the 4 Kolla gnocchi images (C), since nothing else pins them. Mirror any Docker Hub image
whose recorded digest moves under a version tag. Reject B: it needs a new, unmeasured kind loader, and the digests it
writes are only as durable as A's tags or C's mirror anyway.

Not decided here: the bump cadence (weekly proposals, or per release) and whether the release workflow should wait
for `image-scan` (today a release tag runs the scan alongside, not before, publishing).
